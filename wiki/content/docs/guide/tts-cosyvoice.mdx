## 接口概览

`cosyvoice-tts` 是本项目的第 4 个后端服务，基于 [CosyVoice2-0.5B](https://github.com/FunAudioLLM/CosyVoice) 自建
OpenAI 兼容的 `POST /v1/audio/speech`，流式返回**裸 PCM16LE mono @ 24000Hz**（无 WAV 头）。

与 ASR 侧（`funasr-api`/`funasr-ws`）不同，TTS 音色采用**服务端预注册命名音色**：参考音频与其文字转录
全部提前配置在服务端，客户端调用时只传 `{input, voice}`，不接受客户端上传参考音频进行实时克隆。

## 连接参数

| 参数 | 值 | 说明 |
|------|-----|------|
| **Base URL** | `http://<server-ip>/v1/audio/speech` | TTS 合成端点 |
| **API Key** | `funasr-internal` | 内网固定密钥（Nginx 自动注入，与 ASR 侧一致） |
| **Model** | `cosyvoice2` | 固定值，仅一种模型 |

> **内网免配置：** Nginx 统一网关自动注入 `Authorization: Bearer funasr-internal`，客户端不需要显式携带 API Key。

<Callout type="warn" title="网关端口不一定是 80，接入前先确认">
上表的 Base URL 省略了端口，实际端口由部署环境 `.env` 里的 `NGINX_HTTP_PORT` 决定，默认 `80`。

**当前部署服务器（`192.168.31.50`）上是 `9080`**，因为宿主机的 80 端口已被同机运行的 Dokploy traefik 占用。
即完整地址是 `http://192.168.31.50:9080/v1/audio/speech`。

客户端接入前请用 `grep NGINX_HTTP_PORT .env` 或 `docker compose ps nginx` 确认实际映射端口，
不要照搬文档里省略端口的写法。
</Callout>

## 请求格式

```
POST /v1/audio/speech
Content-Type: application/json

{
  "model": "cosyvoice2",
  "input": "要合成的文本",
  "voice": "xiaoxi",          // 服务端预注册的命名音色 id
  "response_format": "pcm",   // 固定 pcm：16-bit LE mono @ 24000Hz，无 WAV 头
  "speed": 1.0,               // 取值范围 0.25 ~ 4.0（与 OpenAI 一致），越界返回 400
  "stream": true              // true: HTTP chunked 流式；false: 整段一次性返回
}
```

响应：`200`，`Content-Type: application/octet-stream`，`Transfer-Encoding: chunked`（`stream=true` 时），body 是裸 PCM16LE mono @ 24000Hz 字节流。

> 用 `application/octet-stream` 而不是 `audio/pcm`，是为了避免中间代理按音频类型做缓冲或转换而破坏流式。客户端按裸 PCM16LE 直接解析即可，不要依赖 Content-Type 判断格式。

未注册音色、空 `input`、`response_format` 不是 `pcm`、`speed` 越界，均返回 `4xx` 并带明确的错误信息，不会静默降级。

## cURL 测试

```bash
# 健康检查（注意 /health 走的是 funasr-api；TTS 自身健康状态用下面这条）
curl http://<server-ip>/health
# TTS 服务状态：device 是 torch 探测到的真实设备，
# 若 device 与 device_requested 不一致，说明 GPU 没挂上，推理会退到 CPU
docker compose exec cosyvoice-tts curl -s localhost:8100/health

# 查看可用音色
curl http://<server-ip>/v1/audio/voices

# 流式合成，保存为裸 PCM 后用 ffplay 播放
curl -s -X POST http://<server-ip>/v1/audio/speech \
  -H 'Content-Type: application/json' \
  -d '{"input":"你好，我是小羲。","voice":"xiaoxi","response_format":"pcm","stream":true}' \
  --output out.pcm

ffplay -f s16le -ar 24000 -ac 1 out.pcm
```

## Python 接入示例

服务返回的是裸 PCM 流，不是标准音频容器格式，因此不能直接用 OpenAI SDK 的 `speech.create()`
写文件后当作 WAV/MP3 播放——需要自己拼流并按 `s16le / 24000Hz / mono` 解释字节：

```python
import requests

resp = requests.post(
    "http://<server-ip>/v1/audio/speech",
    json={
        "input": "你好，我是小羲。",
        "voice": "xiaoxi",
        "response_format": "pcm",
        "stream": True,
    },
    stream=True,
    timeout=300,
)
resp.raise_for_status()

with open("out.pcm", "wb") as f:
    for chunk in resp.iter_content(chunk_size=4096):
        f.write(chunk)

# 如需标准 WAV 文件，可用 wave 模块补上 44 字节头：
import wave
with wave.open("out.wav", "wb") as w:
    w.setnchannels(1)
    w.setsampwidth(2)   # 16-bit
    w.setframerate(24000)
    w.writeframes(open("out.pcm", "rb").read())
```

## 命名音色配置

参考音频与转录全部在服务端，通过环境变量成对声明，`server.py` 启动时自动扫描注册，
新增音色不需要改代码：

```bash
# .env
XIAOXI_PROMPT_WAV=/opt/voices/xiaoxi_16k.wav
XIAOXI_PROMPT_TEXT=参考音频里念的那句话的准确转录
```

约定：`<NAME>_PROMPT_WAV` + `<NAME>_PROMPT_TEXT` 成对出现，`NAME` 小写后即为音色 id
（如 `XIAOXI_*` → 音色 `xiaoxi`）。参考音频要求 **16kHz 单声道 WAV**，配套转录必须逐字准确，
否则会明显拉低合成效果。详细步骤见仓库根目录 `voices/README.md`。

> **合规要求**：参考音频必须是自己录制的，或已获得明确授权的音源，**不得未经同意克隆真实人物的声音**。

## 模型部署（GPU 服务器）

TTS 模型体积较大（数 GB），不随默认的 `download_models.sh` 一起下载，需要单独执行：

```bash
bash scripts/download_models.sh --tts-only
```

模型的实际落盘目录名是 `iic_CosyVoice2-0.5B`（**单个下划线**），不是 `iic/CosyVoice2-0.5B` 子目录。
`cosyvoice-tts` 容器的 `COSYVOICE_MODEL_DIR` 默认值已按此路径配置，一般不需要改动。

<Callout type="info" title="为什么是单个下划线">
`download_models.sh` 用 `tr '/' '__'` 处理 model id。`tr` 是**字符映射**而非字符串替换：
SET1 只有 `/` 一个字符，映射到 SET2 的第一个字符 `_`，多余的 `_` 被忽略。
可以对照服务器上已有的 `iic_SenseVoiceSmall` 目录确认。
</Callout>

## 显存容量提示

`funasr-api`（约 3~4GB/实例）+ `funasr-ws`（4 个模型，占用更高）+ CosyVoice2 fp16（数 GB）
三者共存对 12GB 级显卡（如 RTX 3060）压力较大。**首次部署建议 `--scale-api 1` + 单份 TTS 实例**，
起服务后用 `nvidia-smi` 核实实际显存余量，吃紧时优先考虑分离部署（例如 TTS 单独一台机器）或
降低 `funasr-api` 扩容数，不要盲目 `--scale-api N`。

**实测数字**（RTX 3060 12GB，2026-08-05）：

| 时点 | 显存占用 | 占比 |
|------|---------|------|
| 部署前（全部服务未启动） | 12 MiB | ~0% |
| 启动 `funasr-api` + `funasr-ws` | 3353 MiB（api 1070MB + ws 2258MB） | 27% |
| 再启动 `cosyvoice-tts` | 7218~7320 MiB（+3860~3962MB） | ~60% |

三者共存后余量约 5GB，这块卡上还能再放一份同等大小的模型，但不建议在部署阶段就盲目 `--scale-api N`——显存余量会随请求并发和 batch 情况波动，扩容前务必重新用 `nvidia-smi` 核实。

## 构建与部署实测记录（2026-08-05，RTX 3060 12GB）

首次在真实 GPU 服务器上部署本服务，构建阶段暴露了多个仅能在服务器上复现的问题（本机 macOS 无 GPU 无法预先发现）。以下按面向未来重新构建 / 排障的顺序记录。

### 三个预埋 TODO 的核实结论

1. **基础镜像是否自带 conda** —— **是**。`pytorch/pytorch:2.4.0-cuda12.1-cudnn9-runtime` 自带 conda，`conda install -c conda-forge pynini==2.1.5` 直接可用，实测约 79s（含 conda 自身从 `pkgs/main` 切到 `conda-forge` 索引的一次性升级）。
2. **requirements.txt 在镜像 Python 3.11 下能否全部装上** —— **基本能，但有 5 处需要修复**（见下表），修复后可以正常装完。
3. **ttsfrd 跳过后 wetext 兜底是否正常** —— **2026-08-05 已根治**。最初实测确实不正常：`wetext==0.0.4`（requirements.txt 原始钉版）在 `Normalizer.__init__` 里无条件 `snapshot_download("pengzhendong/wetext")`，而 `pengzhendong/wetext` 是 ModelScope 上的**个人命名空间**仓库，其下载接口返回 `403`（`Authentication token does not exist`）——对照 `iic/SenseVoiceSmall`、`iic/CosyVoice2-0.5B` 两个**官方命名空间**模型的同一接口均 `200` 成功，排除了网络/限流问题，确认是 ModelScope 对个人命名空间仓库的下载要求登录态。根治方案是把 `wetext` 升级到 `0.1.6`：从 `0.0.7` 起官方把 FST 资源文件直接打进 wheel（`package-data`，`importlib.resources` 加载），不再依赖 ModelScope，构建期装完即可用，运行时零联网。已在容器内验证：`Normalizer(remove_erhua=False).normalize('2026年8月5日下午3点，收费128元，涨幅12.5%。')` → `'二零二六年八月五日下午三点，收费一百二十八元，涨幅百分之十二点五。'`，数字/日期/百分号全部正确归一化；服务日志输出 `use wetext frontend`，不再有 `no frontend is avaliable`。详见 Dockerfile 头部注释与下方「国内镜像改造」小节。

### 构建阶段修复的问题

`services/cosyvoice/Dockerfile` 与 `services/cosyvoice/server.py` 在部署过程中暴露并修复了以下问题（均已提交到 `feat/upgrade-and-wiki` 分支）：

| 问题 | 现象 | 修复 |
|------|------|------|
| PEP 668 externally-managed-environment | `scripts/download_models.sh` 里裸 `pip install modelscope` 在 Ubuntu 24.04 + Python 3.12 上报 `externally-managed-environment` | 检测到该错误后补 `--break-system-packages` 重试 |
| `openai-whisper` 缺 `pkg_resources` | legacy `setup.py` 里 `import pkg_resources`，pip 隔离构建环境默认装的最新 setuptools（实测 83.0.0）解析不到该模块，`Getting requirements to build wheel` 阶段 `ModuleNotFoundError` | `PIP_CONSTRAINT` 把隔离构建环境的 setuptools 钉在 `<81` |
| `tensorrt-cu12` / `-bindings` / `-libs` 访问受限 | `-libs` 是 wheel_stub 占位包，硬编码请求 `pypi.nvidia.com`，该域名与 `download.pytorch.org`、`aiinfra.pkgs.visualstudio.com` 一样在这台服务器的网络环境下 TLS 握手失败 | 对照源码确认 `load_trt=False` 时用不到，构建时过滤掉这三个包，不修改 `requirements.txt` 本身 |
| `pyworld` 编译失败 | 没有预编译 wheel，需要现场编译 C++ 扩展，报 `error: command 'g++' failed: No such file or directory` | apt 层加装 `build-essential` |
| `torchvision` 版本未钉导致与 `torch==2.3.1` 不兼容 | requirements.txt 只钉了 `torch`/`torchaudio` 版本，`torchvision` 解析到最新 0.19.0（配 torch 2.4.x），容器启动时 `AttributeError: module 'torch.library' has no attribute 'register_fake'` | 显式重装 `torchvision==0.18.1`（torch 2.3.1 官方配套版本） |
| `deepspeed` 在 runtime 镜像里启动崩溃 | `deepspeed==0.15.1` 装上后 `transformers.modeling_utils` 会无条件 `import deepspeed`，其 `git_version_info.py` 每次 import 都重新执行 CUDA 兼容性检测，要求 `nvcc` 存在；基础镜像是不含开发工具链的 `*-runtime` 变体，容器启动即崩溃重启，报 `CUDA_HOME does not exist` | 对照源码确认推理路径不引用 deepspeed（仅用于分布式训练），构建时过滤掉 |
| pip 大文件下载超时 | `nvidia_cudnn_cu12`（731.7MB）等大 wheel 从 `download.pytorch.org` 下载到一半触发 pip 默认 15s 读超时 | `PIP_DEFAULT_TIMEOUT=120` |
| `add_zero_shot_spk` 传参类型错误（`server.py` 自身的 bug） | 官方签名 `add_zero_shot_spk(prompt_text, prompt_wav, zero_shot_spk_id)` 的 `prompt_wav` 要求文件路径字符串，内部会自行按需要的采样率重新加载；旧代码手动 `load_wav()` 预加载成 tensor 再传入，导致 `torchaudio.load` 收到 tensor 直接 `TypeError`，音色注册 100% 失败 | 改为直接传文件路径，对照官方 `example.py` 用法修正 |
| Nginx 健康检查用 `localhost` 在容器内解析到 IPv6 | `nginx/conf.d/funasr.conf` 只 `listen 80;`，没有监听 IPv6；`wget http://localhost/` 在容器内优先解析到 `::1` 被拒绝连接，导致 nginx 容器持续报 `unhealthy`（服务本身完全正常） | 健康检查显式改用 `http://127.0.0.1/` |

这些问题里，网络访问受限（`tensorrt`/`pypi.nvidia.com` 那条）和大文件超时是这台服务器网络环境相关，其余 6 个是与网络无关的、任何环境重新构建这个镜像都会复现的真实缺陷。

### 耗时与性能实测

- **TTS 模型下载**（`iic/CosyVoice2-0.5B`，ModelScope）：2 分 16 秒，5.3GB（`models/` 目录总占用增至 11GB）
- **镜像构建**（`docker compose build cosyvoice-tts`，含以上所有修复后的完整一次构建）：pip 安装依赖层约 10 分钟（网络状况良好时；构建服务器在部署过程中经历过一次网络波动，未计入此数字），conda/pynini 层约 79 秒，`git clone --recursive` 数秒（视 GitHub 连通性而定）
- **模型加载**（容器启动到 `/health` 就绪）：79.3s（首次冷启动，含 wetext 资源下载重试约 20~30s）/ 5.5s（同镜像重启后的热启动，操作系统页缓存生效）
- **合成短句**（"你好，我是小羲。"，4 字，非流式等效）：96000 字节 = 2.00s 音频，请求总耗时 1.71s（RTF ≈ 0.85）
- **合成长句流式**（约 40 字的句子）：首个音频分片到达 **1.55s**（用 Python 直连服务测得，区别于 curl 的 `time_starttransfer`——后者只反映 HTTP 响应头提交时刻，几乎为 0，不能代表真实首包延迟）；总时长 3.57s 产出 10.08s 音频（RTF ≈ 0.35，约 3 倍实时速度）；模型内部逐分片 RTF 在 0.30~0.45 之间
- **客户端断连**：`curl -m 1` 中断后，日志正确输出「客户端断连，停止 TTS 推理」，GPU 锁立即释放（用紧接着的一次新请求验证，200 响应无需等待），服务健康状态不受影响

### 验证结果

阶段 6 全部验证项目通过：`docker compose ps` 五个服务均 `healthy`；`cosyvoice-tts` 内部 `/health` 返回 `device`/`device_requested` 均为 `cuda`（GPU 确实生效，非静默回退 CPU）；`/v1/audio/voices` 正确返回 `xiaoxi`；4 项边界测试（空 `input`、未注册音色、`response_format=wav`、`speed=0`）均返回 `400` 并带清晰错误信息，无 `500`；ASR 侧 `/health`、`/docs`、`/openapi.json`、根路径状态页、`/ws`（`426 Upgrade Required`）、`/v1/audio/transcriptions`（无文件返回 `422`）均未受新增 TTS 路由影响。

### 国内镜像改造与 wetext 根治（2026-08-05）

`services/cosyvoice/Dockerfile` 的下载源全部换成国内镜像，同一次改动顺带根治了上面的 wetext 问题（升级到 `0.1.6` 后不再依赖任何下载源，国内国外都不需要）。具体改动见 Dockerfile 头部注释，这里只记录**用真实重建镜像验证过的结论**：

| 改动 | 原来 | 现在 | 验证结论 |
|------|------|------|----------|
| `requirements.txt` 第 1 行 extra-index-url | `download.pytorch.org/whl/cu121` | 阿里云 `mirrors.aliyun.com/pytorch-wheels/cu121/` | 已核实存在所需 cp311+cu121 wheel（torch/torchaudio/torchvision），构建成功 |
| `requirements.txt` 第 2 行 extra-index-url | `aiinfra.pkgs.visualstudio.com/...onnxruntime-cuda-12` | 直接删除 | 实测该域名返回 `401`（需要微软内部凭据），任何镜像都代理不了；且实测确认现有 `onnxruntime-gpu==1.18.0` 本来就是从主索引装的，删除这行不改变安装结果 |
| conda 装 pynini | `-c conda-forge`（国外） | `--override-channels -c` 清华 conda-forge 镜像 | 已核实清华镜像有 `pynini==2.1.5` 的 py311 构建 |
| git clone CosyVoice | 直连 GitHub，无法覆盖 | 新增 `COSYVOICE_GIT_MIRROR` build arg，默认仍直连 GitHub，可覆盖 | 推荐值 `https://ghfast.top/https://github.com/` 已实测：主仓库 + `third_party/Matcha-TTS` 子模块（另一个仓库 `shivammehta25/Matcha-TTS`）通过 `git config url.insteadOf` 透明代理，`--recursive` 全量克隆约 16s |
| 基础镜像 `pytorch/pytorch:...` | Docker Hub | **未改动** | 已实测阿里云容器镜像服务对非官方命名空间镜像要求鉴权（`401`），没有可用的公开替代 tag；部署服务器 Docker daemon 本身已配置 `registry-mirrors`（daocloud/nju.edu.cn/dockerproxy 等），`docker pull` 已透明加速，不需要也不应该在 Dockerfile 里硬编码 |
| `wetext` | `0.0.4`（运行时依赖 ModelScope 下载） | `0.1.6`（FST 资源打包进 wheel） | 见上方「三个预埋 TODO 的核实结论」第 3 条 |

**构建耗时对比**（同一台服务器，`docker compose build cosyvoice-tts`，按 buildx 各步骤自报耗时相加）：

| 阶段 | 换源前（`build11.log`，最后一次成功的旧构建） | 换源后（本次） | 变化 |
|------|---:|---:|---:|
| pip 安装依赖（占比最大的一步，含 torch/nvidia-\*/onnxruntime 等大体积 wheel） | 627.4s | 412.0s | **快 215s（约 34%）** |
| conda 装 pynini | 51.2s | 120.2s | 慢 69s |
| git clone --recursive | 10.4s | 66.7s | 慢 56.3s |
| 镜像导出等收尾步骤 | ~21s | ~24s | 基本持平 |
| **合计** | **≈711s（11m51s）** | **≈626s（10m26s，`time` 实测 10m27s）** | **快约 85s（约 12%）** |

国内镜像确实让**耗时占比最大的 pip 安装阶段**显著变快（这是核心收益，验证了"所有下载源优先国内源"的预期）；conda 与 git clone 两步这次实测反而更慢，但这两步本身耗时基数小（各在 1~2 分钟量级），且 git clone 默认值没变（仍是直连 GitHub，未启用镜像 build arg），这两步的波动更可能是网络抖动而非镜像改造导致的系统性变慢——不排除后续重建时数字会反过来，两步耗时太小不足以下"更慢"的结论，需要更多样本才能定论。

<Callout type="info" title="重建过程中发现的一个预置限制：onnxruntime CUDA EP 加载失败，不影响服务">
新镜像启动日志里能看到一条 onnxruntime 报错：`Failed to load library libonnxruntime_providers_cuda.so with error: libcublasLt.so.11: cannot open shared object file`——`onnxruntime-gpu==1.18.0`（requirements.txt 钉的版本）在 PyPI/清华镜像上发布的是面向 CUDA 11 的构建（这正是那条被删除的 aiinfra extra-index-url 原本想解决的问题：提供一个 CUDA 12 专用构建，但该源本身已经不可达），而镜像里只有 CUDA 12 的 `libcublasLt.so.12`，两者版本不匹配，onnxruntime 自动降级到 CPU 执行。

这**不是本次改动引入的回归**：aiinfra 源在改动前后都是不可达的（未改前它同样装不上，只是构建日志里没有单独记录这次探测失败），改动前后实际装到的都是同一个 CUDA-11-targeted 的 `onnxruntime-gpu` wheel。也**不影响生产请求路径**：这个 CUDA 执行器只被 `frontend.py` 的 `_extract_speech_token`（走 `speech_tokenizer_session`）用到，而这个方法只在**首次注册命名音色**（`add_zero_shot_spk`，容器启动时跑一次）时调用；`server.py` 的 `/v1/audio/speech` 每次请求走的是 `zero_shot_spk_id` 非空分支（`inference_zero_shot(..., zero_shot_spk_id=voice)`），直接复用启动时算好的 `spk2info`，完全不会在请求时触发这个 ONNX session。实测音色注册（`已注册命名音色: xiaoxi`）与合成本身都正常，RTF 与历史数据一致，未观察到性能回退。记录在此是为了如实说明，不是掩盖问题——如果未来有场景需要真正的 ad-hoc zero-shot（`zero_shot_spk_id=''`），这个 CPU 回退会成为那条路径的瓶颈，需要单独解决（比如换一个显式声明 cu12 支持的 onnxruntime-gpu 版本）。
</Callout>

### 首包延迟优化：首片切分（2026-08-05）

<Callout type="warn" title="更正此前结论">
本节此前写过"首包延迟稳定在 1.49~1.60s，不随文本变长而线性增长，不需要切句优化"——**这个结论是错的**，
被后续更细粒度的实测推翻。当时用的 8/29/44/99/227 字样本首字都恰好落在 CosyVoice 内部
`split_paragraph()` 切出的同一个分片长度区间内，掩盖了首包延迟其实随**第一个分片的文本长度**增长的
真实规律。下面是更正后的机制说明与实测数据。
</Callout>

首包延迟的本质是合成**第一个分片**所需的时间（LLM prefill 成本 + 声学解码），与分片本身的文本长度
正相关，不是恒定值。问题出在 CosyVoice 的 `frontend.py`：`split_paragraph(..., token_min_n=60,
token_max_n=80, comma_split=False)` **不把逗号当切分点**，只在句号/问号/感叹号等断句符处切分。
逗号密集但没有句号的长句（比如"今天天气很好，我们一起去公园散步吧，那里有很多漂亮的花朵和绿树，
空气也特别清新宜人。"，42 字，直到句尾才有第一个可切分点）会被整体当成一个分片合成，首包要等**整句**
合成完。

**优化实现**：`services/cosyvoice/server.py` 在提交给 CosyVoice 之前，先按中文标点（`，,。？！；：、.?!;`，
**包含逗号**）切出用户输入的第一个短片段（长度上限由 `TTS_FIRST_CHUNK_MAX_CHARS` 控制，默认 15 字），
单独调一次 `inference_zero_shot` 先合成吐出；剩余文本再整体调一次，交给 CosyVoice 自己的默认策略切分。
`inference_zero_shot` 内部本来就是 `for i in texts: self.model.tts(...)` 逐段独立调用，段与段之间没有
跨段状态，所以我们自己多切这一刀在韵律上和 CosyVoice 自己切完全等价，不会引入新的断裂。输入本身短于
阈值时不切，保持原来的单次调用，不引入无谓的二次请求开销。

<Callout type="info" title="配置项">
`TTS_FIRST_CHUNK_MAX_CHARS`（`.env`，默认 `15`）：首片最大字符数上限。设为 `0` 或负数关闭此优化，
退回"整段一次性调用"的原行为，作为出问题时的快速回退开关。
</Callout>

**实测对比**（部署服务器 RTX 3060 12GB，同一批文本各跑 3 次取中位数，完整方法与边界回归见
[AI Agent 接入 TTS](/docs/guide/agent-tts-integration) 的实测表格）：

| 文本 | 字数 | 优化前首包 | 优化后首包 | 降幅 | 优化前总耗时 | 优化后总耗时 | 优化前音频时长 | 优化后音频时长 |
|------|-----:|----------:|----------:|-----:|----------:|----------:|----------:|----------:|
| 你好。 | 3 | 0.637s | 0.625s | ~持平（未触发切分） | 0.638s | 0.626s | 0.96s | 1.12s |
| 你好，我是小羲，很高兴认识你。 | 15 | 1.126s | 1.16s | ~持平（未触发切分，全文=阈值） | 1.423s | 1.161s | 3.44s | 3.52s |
| 今天天气很好，……空气也特别清新宜人。 | 42 | 1.585s | 0.815s | **-48.6%** | 3.49s | 3.25s | 9.64s | 9.44s |
| 上一行重复 3 遍 | 126 | 1.528s | 0.77s | **-49.6%** | 10.453s | 10.259s | 26.84s | 27.88s |

42 字与 126 字两个逗号密集、句号靠后的长句样本首包延迟接近腰斩，与决定性对照实验一致（首片被切出的
恰好是第一个逗号分句"今天天气很好，"，7 字，触发日志 `TTS 首包优化触发：切出首片 7 字，剩余 …`）。
15 字全句样本因为**整句长度等于阈值**（`len(text) <= max_chars` 时不切），行为与优化前一致，符合预期。
**真正触发切分的两行（42 字 / 126 字）音频总时长偏差在 ±5% 以内**（9.64→9.44s、26.84→27.88s），
**没有观察到切分引入额外停顿的证据**；总耗时也没有因为多一次 GPU 调用而变差，反而因为首片短、
启动更快而略有下降。

未触发切分的行不能同样解读：「你好。」的音频时长从 0.96s 变成 1.12s（+16.7%），但这一行压根没走切分
路径（3 字 < 阈值），前后是同一段代码。差异来自 CosyVoice 的 LLM 采样解码——同一段文本每次合成出的
时长本就有波动。**约 ±17% 是该模型单次合成时长的天然噪声水平**，评估切分副作用时要以此为基线，
小于这个量级的差异不构成有意义的信号。下面阈值 12 的 +18% 之所以能被判定为真实劣化，是因为它同时
伴随「本就紧凑的短句被强行切开」这一可解释的机制，而不是仅凭数字大小。

**为什么默认阈值是 15 而不是更激进的 12**：额外测过 `TTS_FIRST_CHUNK_MAX_CHARS=12`，15 字全句样本会被
强制切成"你好，"（3 字）+ 剩余 12 字两段——首包延迟确实进一步降到 0.558s，但**音频总时长从 3.52s
涨到 4.16s（+18%）**，明显超过 5% 的判断线，是切分引入额外停顿的客观证据：把一个本来就很短、语义
连贯的短句强行切成 3 字 + 12 字两段，段间会产生原本没有的停顿。而两个长句样本（首个逗号分句固定在
7 字）在 12 与 15 两档阈值下切分结果完全相同，收益无差别。综合看，**15 字是更安全的默认值**：既能
完整拿到长句场景的首包收益，又不会因为阈值过低而误伤本来就短的完整句子。

## 与 ASR 接口的关系

`/v1/audio/speech` 与 `/v1/audio/voices` 是精确路径的 Nginx location，按最长前缀匹配
优先于更短的 `/v1/`，因此不会与 ASR 侧的 `/v1/*`（转写、`/v1/models` 等）冲突，两套后端各自独立。
